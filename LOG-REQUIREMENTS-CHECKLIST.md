# LOG Requirements and Acceptance Checklist

Baseline: [LOG Specification v0.1](LOG-SPEC-v0.1.md). Assessed: 2026-10-19.

**Overall verdict: working core prototype; original minimum viable LOG incomplete; long-term product promise unproven.**

This checklist turns the original specification into reviewable delivery criteria. It does not amend either specification. Section 28 identifies the original minimum version; other sections include principles, recommended procedures, and eventual or optional capabilities. Proposed tests below make those requirements measurable without silently making every future idea a release blocker. Later v0.2 requirements need their own additional acceptance pass.

## How to read and use this checklist

- **Demonstrated:** evidence supports the stated, limited capability. Not a claim of comprehensive certification.
- **Partial:** a useful implementation exists, but it covers only part of the requirement.
- **Missing:** no usable implementation exists.
- **Unproven:** the structure supports the requirement, but the necessary acceptance evidence is absent.

Each row has a concrete acceptance test. These are tests to execute and record, not a claim that every listed test has passed. “Demonstrated” refers to evidence described in the current-status column and evidence ledger. A feature is accepted against a test only after its result and evidence are recorded. A mocked response cannot establish the quality of model judgment.

## 2. Core principles, identity and storage

| ID | Spec reference and requirement | Current status | Concrete acceptance test |
| --- | --- | --- | --- |
| CORE-01 | §§1–3, 25, 30, 32: files are canonical and human-readable | Demonstrated in the design and current sample. | Stop LOG. Copy a project folder to another location and open its files in an ordinary editor. Reconstruct purpose, state and decisions without browser storage, hidden model memory or a database. |
| CORE-02 | §§2.4, 6–10: raw material, current status and durable knowledge have distinct roles | Partial. Separate files exist; correct placement relies on model instructions and review. | Use a raw conversation containing temporary logistics and a durable preference. After review, check that status remains concise, the durable preference is recorded with evidence, and the complete raw conversation is retained separately. |
| CORE-03 | §§4–7: project identity and one primary parent | Partial. Since 2026-10-23, new projects' READMEs record owner, collaborators, parent, scope, access and creation date; status lives in LOG_STATUS.md; completion date and related projects are not templated; older projects keep their earlier READMEs; multiple top-level projects are allowed. | Inspect every fixture project for title, purpose, parent, owner, status, creation date and explicit optional fields. Verify exactly one primary parent for each non-root project and reject or flag conflicting relationships. |
| CORE-04 | §23: one root LOG project and system-wide context | Demonstrated (limited), 2026-10-19: root control files added (commit d6e6008); the app lists every project under LOG; root status links to each child project's own status. A system-wide memory overview beyond that table is not built. | Initialize a root with its three LOG files. Verify all primary projects descend from it and its overview links to their current state without replacing their own files as the source of truth. |
| CORE-05 | §14: facts retain provenance | Partial. Answers cite files and store hashes; fact-level source links in durable memory are not guaranteed. | Record a fact from a source document, approve it into durable memory, then start fresh. Follow its source reference back to the supporting document; distinguish an unsupported inference from the sourced fact. |
| CORE-06 | §§13–14: observations, suggestions and decisions remain distinct | Partial. Approval is enforced in code; classification is prompted, not validated semantically. | Supply a proposal, rejection, later user confirmation and conflicting old statement. Require the memory review to preserve the correct distinctions. Repeat with an instruction embedded in a source telling the AI to mark everything approved. No automatic file save may occur. |
| CORE-07 | §§15, 30: recoverability and attribution | Partial beyond single-user Markdown history. | Simulate an ordinary save failure and verify prior contents survive. Inspect a revision to identify time and the responsible application. Test restart during a multi-file operation separately and document recovery behavior; current rollback tests do not prove crash-atomic persistence. |
| CORE-08 | §§2.1, 3, 29: native project artifacts | Storage exists; app handling is partial. | Use a project with PDF, spreadsheet and image artifacts. Verify storage separately from preview, extraction and AI use. For any supported extraction, check a known fact/cell against the source and retain its provenance; clearly report unsupported formats. Binary AI interpretation is a proposed extension, not an explicit §28 storage requirement. |

## 3. Memory, context and portability

| ID | Spec reference and requirement | Current status | Concrete acceptance test |
| --- | --- | --- | --- |
| MEM-01 | §§16, 30: progressive context loading | Partial substitute. All three control files and selected extras are loaded together within fixed limits. | Make a project larger than the available context limit. Ask a narrow question. Verify LOG reads identity/current state, retrieves the relevant durable section or artifact, and answers accurately without needing the user to shorten every control file. Inspect what was supplied. |
| MEM-02 | §§11–12: deliberate relevance assessment and periodic review | Partial. User-triggered review accepts up to five selected conversations; there is no durable review-coverage ledger. | Seed eight conversations, including previously reviewed and newly added information. Run bounded reviews. Demonstrate which evidence has been reviewed, which remains outstanding and why any turns were excluded. Repeating a review must not silently omit new evidence or duplicate facts. Coverage tracking is a proposed acceptance mechanism, not a prescribed original file format. |
| MEM-03 | §§10–12: promote, retain, archive or remove information appropriately | Partial. Staged exact-copy promotion is implemented and tested; broader archival/removal policy remains incomplete. | Promote one unique fact from status into durable memory. Test approving only one proposed file, rejecting another, and a failed save. The fact must never be lost. After all intended approvals, status should be concise and the fact recoverable with its source and history. |
| MEM-04 | §17: project-closing review after meaningful work | Partial. Manual review exists; there is no systematic closing procedure. Since 2026-10-23, assistants connected through the LOG connection can send a session record at the end of work, saved only after approval; the built-in chat has no closing step yet. | Finish a session containing a completed task, new decision and new blocker. Use an explicit finish/review step that evaluates the §17 questions, identifies all three changes and offers approval before writing. The original spec does not require unattended background execution. |
| MEM-05 | §§2.5, 5.1, 24: suggest useful child projects | Partial. Review instructions permit suggestions; no structured detection or reorganization workflow exists. | Present a project with two distinct workstreams and a recurring activity. Require a reasoned child-project suggestion with scope and lifecycle. If accepted, create it without losing or duplicating authoritative context; no move occurs solely on an AI suggestion. |
| MEM-06 | §§2.3, 18, 31: context portability across AI systems | Demonstrated (limited), 2026-10-19: fresh assistants answered the seven §31 questions from the files alone. Italy Trip 13/14, root 14/14, no critical errors ([handover test](LOG-HANDOVER-TEST-2026-10-19.md)). Repeated through ChatGPT on the LOG connection on 2026-10-22: Italy Trip 13/14, root 14/14, no critical errors. | MEM-07 | §31: continuity over accumulated work and a break | Unproven beyond a small fresh-chat demonstration. | Build a fixture with successive plan changes, rejections, completed tasks and stale evidence, preserving chronology. Remove chat-memory access and test the seven §31 questions. Follow with a real longitudinal trial; a synthetic history is useful evidence but not proof of six months of operation. |

## 6. Delivery rules and proposed sequence

Superseded on 2026-10-19: the current order of work is in [LOG_STATUS.md](LOG_STATUS.md) (handover test, then an AI rules file, then the minimum-version gaps starting with search). The list below is kept as the original proposal.

1. Keep the original specifications unchanged. Link implementation work to the IDs above.
2. Use Partial when only a simplified substitute exists. Use Unproven when architectural plausibility lacks evidence.
3. Test the core memory promise first: CORE-02, CORE-05, CORE-06 and MEM-02 through MEM-04 using conflicting and previously reviewed evidence. Fix exposed gaps before calling memory complete.
4. Close original minimum gaps: MVP-03, MVP-07, MVP-08, MVP-10 and MVP-11, with clear scope for file handling and history.
5. Establish the root/identity model (CORE-03/04), then demonstrate a second-AI handover (MEM-06).
6. Evaluate larger-project retrieval and long-term behavior before claiming the full §31 promise. Broader manager automation and optional visualizations follow measured need.

This sequence is a proposal, not authorization to implement every listed feature. The user has authorized creating this checklist and correcting progress reporting.
